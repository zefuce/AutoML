# Анализ пользовательского запроса

## Цель

Цель анализа пользовательского запроса — преобразовать описание задачи на\
естественном языке в структурированное представление требований пользователя к ML-\
задаче. Это представление используется вместе с результатами анализа датасета для\
последующего формирования конфигурации AutoGluon.

## Этапы анализа

1. Определение границ задачи
2. Определение извлекаемой информации
3. Классификация информации
4. Анализ пользовательских формулировок
5. Обработка неоднозначностей и конфликтов
6. Формат структурированного результата
7. Примеры запросов

---

### 1. Определение границ задачи

На вход система получает пользовательский запрос на русском языке,\
содержащий описание ML-задачи и требований к ней. На выходе формируется\
структурированное описание сведений, которые можно обоснованно получить\
из текста запроса.\
Анализ запроса не подменяет анализ датасета и не формирует готовые параметры\
AutoGluon. Например, пользователь может попросить «предсказывать стоимость\
квартиры», но точное имя соответствующего столбца устанавливается только после\
просмотра данных.\
В рамках основной версии проекта рассматриваются задачи бинарной и многоклассовой\
классификации и регрессии на одной размеченной таблице. Запросы на кластеризацию,\
прогнозирование временных рядов как отдельную задачу, работу с изображениями и\
другие неподдерживаемые сценарии должны распознаваться как выходящие за границы\
проекта, а не автоматически сводиться к классификации или регрессии.

Общая схема:  

`Запрос пользователя` &#8594; `извлечение требований` &#8594; `структурированное описание` &#8594;\
`сопоставление с датасетом и проверка` &#8594; `конфигурация AutoGluon`

### 2. Определение извлекаемой информации

При анализе пользовательского запроса необходимо выделять сведения, характеризующие\
постановку ML-задачи, требования и ограничения пользователя.

**Постановка задачи:**
- цель задачи;
- тип решаемой ML-задачи, если его можно определить из текста;
- целевую переменную в формулировке пользователя.

**Требования к качеству:**
- требования к качеству и приоритеты ошибок;
- явно указанную метрику, если она названа.

**Ограничения:**
- ограничения по времени обучения;
- ограничения по времени предсказания;
- ограничения по используемым ресурсам.

**Требования к модели:**
- требования к интерпретируемости;
- требования к размеру или сложности модели;
- необходимость исключить определённые признаки;
- требования к разделению данных, если пользователь их обозначил.

**Дополнительные требования и контекст:**
- требования к итоговому результату;
- сведения о предметной области, времени наблюдений, группах объектов и условиях\
будущего применения модели, если они приведены в запросе.

Эти пункты описывают то, что следует искать в запросе, а не обязательные настройки\
AutoGluon. Часть требований может остаться текстовой и потребовать дополнительной\
интерпретации.

### 3. Классификация информации

Извлекаемую информацию можно разделить на четыре типа:

| Тип информации | Описание                                  |
| -------------- | ----------------------------------------- |
| Явно указанная | напрямую присутствует в запросе           |
| Выводимая      | однозначно определяется из смысла запроса |
| Неуказанная    | отсутствует в запросе                     |
| Неоднозначная  | допускает несколько интерпретаций         |

Такое разделение позволяет не смешивать слова пользователя\
с решениями, которые система принимает самостоятельно после анализа данных.

Отсутствие значения в запросе не означает, что итоговый параметр AutoGluon тоже\
должен остаться пустым: на этапе конфигурирования возможно использование\
подходящего значения по умолчанию. Оно не должно ошибочно помечаться как\
извлечённое из запроса.

### 4. Анализ пользовательских формулировок

Один и тот же параметр может быть описан пользователем разными способами:

- «предсказать стоимость» &#8594; задача прогнозирования числового значения;
- «определить, уйдет клиент или нет» &#8594; задача с двумя возможными классами;
- «обучение не дольше 10 минут» &#8594; ограничение по времени обучения;
- «модель должна быть понятной» &#8594; требование к интерпретируемости;
- «важнее не пропустить мошенническую операцию» &#8594; приоритет определённого вида ошибок,\
но не явное указание recall;
- «не используй номер клиента» &#8594; требование исключить признак, имя которого ещё нужно\
сверить с датасетом;
- «данные собраны по месяцам, проверять нужно на более поздних периодах» &#8594; контекст для выбора\
разбиения, а не готовый аргумент fit().

Поэтому система должна работать не только с ML-терминами, но и с обычными формулировками.\
Выбор конкретной метрики или стратегии валидации на основе этих требований происходит\
на следующем этапе, с учётом датасета и поддерживаемой конфигурации.

### 5. Обработка неоднозначностей и конфликтов

Для проблемных случаев необходимо заранее определить правила поведения системы:

| Ситуация                                        | Действие системы                                                                                       |
| ----------------------------------------------- | ------------------------------------------------------------------------------------------------------ |
| Информации недостаточно                         | Оставить соответствующее значение неопределённым;<br>перед конфигурированием оценить, достаточно ли<br> безопасного значения по умолчанию или требуется<br>уточнение |
| Возможны несколько трактовок                    | Сохранить статус неоднозначности, не выдавать<br>предположение за факт                                 |
| Требования противоречат друг другу              | Зафиксировать конфликт и исходные формулировки; не выбирать<br>одно из противоречащих значений без разрешения конфликта |
| Формулировку нельзя сопоставить с<br>параметром | Сохранить исходное требование для последующей<br>обработки или объяснения ограничений                  |
| Запрос выходит за рамки проекта                 |	Явно отметить неподдерживаемую задачу и не запускать её<br>под видом другой постановки                 |

Главный принцип - не добавлять в структурированный результат информацию,\
которую нельзя обоснованно получить из запроса пользователя.

На следующем этапе система сопоставляет требования с датасетом. При отсутствии\
целевого столбца, риске утечки, конфликте с доступными признаками или недостаточной\
информации для корректного запуска необходимо предупреждение либо уточняющий вопрос.\
Проверки не гарантируют выявления всех предметных ошибок.

### 6. Формат структурированного результата

Результат анализа запроса используется для дальнейшего формирования конфигурации\
AutoML, но не передаётся непосредственно в AutoGluon. Он отражает содержание запроса,\
а не окончательно выбранные параметры обучения.

Для каждого извлеченному значения необходимо сохранять статус его определения:

- explicit  - явно указано пользователем;
- inferred  - однозначно выведено из запроса;
- unknown   - невозможно определить из запроса;
- ambiguous - допускает несколько трактовок.

Значения, которые невозможно установить из запроса, не заполняются предполагаемыми\
параметрами AutoGluon. Если требования противоречат друг другу, их исходные\
формулировки сохраняются в `conflicts`. Обязательные противоречия разрешаются до\
запуска обучения.

Пример структуры для первого сценария из раздела 7:
```json
{
  "goal": { 
    "value": "предсказывать стоимость квартиры", 
    "status": "explicit" 
  },
  "task_type": {
    "value": "regression",
    "status": "inferred"
  },
  "target": {
    "value": "стоимость квартиры",
    "status": "explicit"
  },
  "metric": { 
    "value": null, 
    "status": "unknown" 
  },
  "constraints": {
    "training_time": {
      "value": "не больше 10 минут",
      "status": "explicit"
    }
  },
  "requirements": {
    "interpretability": {
      "value": null,
      "status": "unknown"
    }
  },
  "conflicts": []
}
```

Это промежуточное представление требований. Окончательная конфигурация содержит\
проверенные имена столбцов, допустимые значения параметров и применённые\
настройки по умолчанию.

### 7. Примеры запросов

**Пример 1**

Запрос:

> «Хочу предсказывать стоимость квартиры. Обучение должно занимать не больше 10\
> минут».

Извлеченная информация:

- цель - предсказание стоимости квартиры **(explicit)**;
- тип задачи - регрессия **(inferred)**;
- целевая переменная - стоимость квартиры **(explicit)**; точное имя\
столбца пока неизвестно;
- максимальное время обучения - 10 минут **(explicit)**;
- метрика - не указана **(unknown)**;
- требование к интерпретируемости - не указано **(unknown)**.

**Пример 2**

Запрос:

> «Нужно определить, уйдет клиент или нет. Важно не пропускать клиентов, которые\
> собираются уйти».

Извлеченная информация:

- цель - определение ухода клиента **(explicit)**;
- тип задачи - бинарная классификация **(inferred)**;
- целевая переменная - факт ухода клиента **(inferred)**; имя столбца\
пока неизвестно;
- особое требование к качеству - не пропускать клиентов, склонных\
к уходу **(explicit)**;
- метрика - не указана **(unknown)**.

**Пример 3**

Запрос:

> «Нужна простая и понятная модель для оценки кредитного риска».

Извлеченная информация:

- цель - оценка кредитного риска **(explicit)**;
- тип задачи - неоднозначен **(ambiguous)**;
- целевая переменная - не указана **(unknown)**;
- требование к интерпретируемости - понятная модель **(explicit)**;
- требование к низкой сложности модели - простая модель **(explicit)**.

### Связь с конфигурацией ML-пайплайна

Результат анализа запроса используется при формировании конфигурации ML-пайплайна.\
Конкретные параметры конфигурации определяются на основе полученной информации,\
характеристик датасета и настроек системы.

Подробная структура финальной конфигурации и правила проверки описаны в документе\
[Конфигурация](./configuration.md).
