# Анализ пользовательского запроса

## Цель

Цель анализа пользовательского запроса - преобразовать запрос на естественном языке\
в структурированное представление требований пользователя к ML-задаче.

## Этапы анализа

1. Определение границ задачи
2. Определение извлекаемой информации
3. Классификация информации
4. Анализ пользовательских формулировок
5. Обработка неоднозначностей и конфликтов
6. Формат структурированного результата
7. Примеры запросов

---

### 1. Определение границ задачи

На вход система получает пользовательский запрос на естественном языке,\
содержащий описание ML-задачи и требований к ней.\
Результатом анализа должно быть структурированное представление информации,\
которую удалось получить из запроса.\
Важно отделять требования пользователя от параметров ML-конфигурации, которые система\
будет выбирать самостоятельно при дальнейшем построении пайплайна.

Общая схема:  

`Запрос пользователя` &#8594; `извлечение информации` &#8594; `структурированное описание`\
`требований` &#8594; `конфигурация ML-пайплайна`

### 2. Определение извлекаемой информации

При анализе пользовательского запроса необходимо выделять сведения, характеризующие\
постановку ML-задачи, требования и ограничения пользователя.

**Постановка задачи:**
- цель задачи;
- тип решаемой ML-задачи;
- целевая переменная.

**Требования к качеству:**
- требования к качеству модели;
- указанную метрику.

**Ограничения:**
- ограничения по времени обучения;
- ограничения по времени предсказания;
- ограничения по используемым ресурсам.

**Требования к модели:**
- требования к интерпретируемости;
- требования к размеру или сложности модели.

**Дополнительные требования и контекст:**
- требования к итоговому результату;
- дополнительный контекст о данных или области применения.

### 3. Классификация информации

Извлекаемую информацию можно разделить на четыре типа:

| Тип информации | Описание                                  |
| -------------- | ----------------------------------------- |
| Явно указанная | напрямую присутствует в запросе           |
| Выводимая      | однозначно определяется из смысла запроса |
| Неуказанная    | отсутствует в запросе                     |
| Неоднозначная  | допускает несколько интерпретаций         |

Такое разделение позволяет не смешивать слова пользователя\
с решениями, которые система принимает самостоятельно.

### 4. Анализ пользовательских формулировок

Один и тот же параметр может быть описан пользователем разными способами:

- «предсказать стоимость» → задача прогнозирования числового значения;
- «определить, уйдет клиент или нет» → задача с двумя возможными классами;
- «обучение не дольше 10 минут» → ограничение по времени обучения;
- «модель должна быть понятной» → требование к интерпретируемости;
- «важнее не пропустить мошенническую операцию» → особое требование к качеству результата.

Поэтому система должна работать не только с ML-терминами,\
но и с обычными пользовательскими формулировками.

### 5. Обработка неоднозначностей и конфликтов

Для проблемных случаев необходимо заранее определить правила поведения системы:

| Ситуация                                                   | Действие системы                                                              |
| ---------------------------------------------------------- | ----------------------------------------------------------------------------- |
| Информации недостаточно                                    | оставить параметр неопределенным или<br>запросить уточнение                   |
| Возможны несколько трактовок                               | сохранить неоднозначность и не выбирать<br>значение без достаточных оснований |
| Требования противоречат друг другу                         | зафиксировать конфликт и запросить<br>уточнение                               |
| Формулировку нельзя однозначно<br>преобразовать в параметр | сохранить исходное требование для<br>дальнейшей обработки                     |

Главный принцип - не добавлять в структурированный результат информацию,\
которую нельзя обоснованно получить из запроса пользователя.

### 6. Формат структурированного результата

Результат анализа запроса должен быть представлен в структурированном формате,\
который можно использовать при формировании конфигурации AutoML.

Для каждого параметра необходимо сохранять статус его определения:

- explicit  - значение явно указано пользователем;
- inferred  - значение однозначно выведено из запроса;
- unknown   - значение определить невозможно;
- ambiguous - значение неоднозначно.

Если в запросе есть противоречащие друг другу требования, их исходные значения сохраняются,\
а конфликт отдельно отмечается в массиве `conflicts`. До разрешения конфликта система\
не выбирает одно из противоречащих значений.

Пример:
```json
{
  "goal": { 
    "value": "предсказывать стоимость квартиры", 
    "status": "explicit" 
  },
  "task_type": {
    "value": "regression",
    "status": "inferred"
  },
  "target": {
    "value": "стоимость квартиры",
    "status": "explicit"
  },
  "metric": { 
    "value": null, 
    "status": "unknown" 
  },
  "constraints": {
    "training_time": {
      "value": "не больше 10 минут",
      "status": "explicit"
    }
  },
  "requirements": {
    "interpretability": {
      "value": null,
      "status": "unknown"
    }
  },
  "conflicts": []
}
```

### 7. Примеры запросов

**Пример 1**

Запрос:

> «Хочу предсказывать стоимость квартиры. Обучение должно занимать не больше 10\
> минут».

Извлеченная информация:

- цель - предсказание стоимости квартиры - явно указано;
- тип задачи - регрессия - выведено из запроса;
- целевая переменная - стоимость квартиры - явно указано;
- максимальное время обучения - 10 минут - явно указано;
- метрика - не указана;
- требование к интерпретируемости - не указано.

**Пример 2**

Запрос:

> «Нужно определить, уйдет клиент или нет. Важно не пропускать клиентов, которые\
> собираются уйти».

Извлеченная информация:

- цель - определение ухода клиента - явно указано;
- тип задачи - бинарная классификация - выведено из запроса;
- целевая переменная - факт ухода клиента - явно указано;
- особое требование к качеству - не пропускать клиентов, склонных к уходу - явно указано;
- метрика - не указана.

**Пример 3**

Запрос:

> «Нужна простая и понятная модель для оценки кредитного риска».

Извлеченная информация:

- цель - оценка кредитного риска - явно указано;
- тип задачи - неоднозначен;
- целевая переменная - не указана;
- требование к интерпретируемости - понятная модель - явно указано;
- требование к низкой сложности модели - простая модель - явно указано.

### Связь с конфигурацией ML-пайплайна

Результат анализа запроса используется при формировании конфигурации ML-пайплайна.\
Конкретные параметры конфигурации определяются на основе полученной информации,\
характеристик датасета и настроек системы.

Описание параметров приведено в документе [Конфигурация](./configuration.md).
