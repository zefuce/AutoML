# AH-02 - Проверка модели на более поздних продажах

**Датасет:** Ames Housing (`train.csv`)  
**Категория:** длинный  

## 1. Входные данные

**Запрос пользователя:**

> «У нас накоплена история сделок с жилой недвижимостью за несколько лет. Я хочу не просто случайно поделить объекты на обучение и тест, а проверить, как модель поведёт себя на продажах, которые произошли позже тех, на которых она училась. Поэтому давайте разделим данные по годам и месяцам продажи. Только учтите, что в реальной работе мы оцениваем объект заранее: неизвестные на момент оценки условия будущей сделки нельзя бездумно использовать как признаки. Меня интересует воспроизводимая схема проверки, а не максимальная цифра качества на перемешанных строках.»

**Вход для будущего теста:** исходный `train.csv` вместе с приведённым выше текстом.

## 3. Ручное решение и конфигурация

- **Задача:** предложить прогноз `SalePrice` с `problem_type = "regression"`, поскольку это размеченная числовая цель в исходном `train.csv`, и уточнить, именно ли её нужно предсказывать. До подтверждения не считать задачу окончательно установленной.
- **Временная проверка:** `YrSold` и `MoSold` позволяют расположить сделки по году и месяцу. По EDA представлены 2006-2010 годы, причём в 2010 году 175 продаж. Пример внешней проверки: обучение на сделках 2006-2009 годов и независимый тест на 2010 году. Границу зафиксировать до обучения; строки не перемешивать, один месяц не делить между train и test.
- **Признаки:** `Id` не использовать для обучения. `SaleType` и `SaleCondition` требуют проверки доступности до сделки; фактические `YrSold` и `MoSold` служат для разделения данных, но не обязательно известны заранее как прогнозные признаки. В кандидате все эти поля консервативно исключены из признаков.
- **Метрика и валидация:** если подтвердится регрессия по `SalePrice`, допустима `mean_absolute_error` либо `root_mean_squared_error`. Внешнее хронологическое разбиение выполняет сервис до AutoGluon; `validation_procedure = "auto"` управляет только внутренней валидацией на обучающем периоде и не обеспечивает временное разделение сам по себе.

**Кандидат конфигурации** (после указанных проверок):

```json
{
  "label": "SalePrice",
  "problem_type": "regression",
  "eval_metric": "mean_absolute_error",
  "ignored_columns": [
    "Id",
    "SaleType",
    "SaleCondition",
    "MoSold",
    "YrSold"
  ],
  "validation_procedure": "auto",
  "presets": "medium_quality"
}
```

Приведённая конфигурация условна: сначала нужно подтвердить, что прогнозируется именно `SalePrice`, и определить доступные до сделки поля. Для полноценной временной настройки можно отдельно выделить более позднюю часть обучающего периода под валидацию; реализация требует логики сервиса, а не одного `holdout_frac`.

## 4. Критерии проверки агента

- **Обязательные результаты:** агент сохраняет требование хронологической проверки, использует `YrSold` и `MoSold` для порядка сделок, не смешивает будущие продажи с обучением, проверяет доступность признаков и уточняет неуказанную цель прогнозирования.
- **Допустимые альтернативы:** другая обоснованная граница между прошлыми и будущими периодами; более поздний месяц или год для независимого теста; выбор MAE либо RMSE после подтверждения регрессионной цели.
- **Критические ошибки:** считать случайное разбиение выполнением требования; выбирать таргет из текста как явно заданный; использовать сведения о будущей сделке как признаки без проверки; принимать `validation_procedure` или `holdout_frac` за автоматическую временную валидацию.
