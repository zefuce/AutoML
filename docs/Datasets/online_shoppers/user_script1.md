# OS-01 - Прогноз покупки при входе посетителя на сайт

**Датасет:** Online Shoppers Purchasing Intention (`online_shoppers_intention.csv`)  
**Категория:** короткий  

## 1. Входные данные

**Запрос пользователя:**

> «Покупка или нет — хочу понять прямо при входе посетителя на сайт, пока он еще ничего не успел посмотреть.»

**Вход для будущего теста:** исходный `online_shoppers_intention.csv` вместе с приведённым выше текстом.

## 3. Ручное решение и конфигурация

- **Задача:** По EDA целевой столбец `Revenue` отражает факт покупки, `problem_type = "binary"`, положительный класс - `True` (15,47% сессий). Это итог сессии, а не текущая покупка в момент входа.
- **Признаки:** Для прогноза до просмотра страниц исключить `Administrative`, `Administrative_Duration`, `Informational`, `Informational_Duration`, `ProductRelated`, `ProductRelated_Duration`, `BounceRates`, `ExitRates` и `PageValues`: эти показатели относятся к посещённым страницам либо рассчитываются по ходу сессии. Доступность `Month`, `Weekend`, `SpecialDay`, `OperatingSystems`, `Browser`, `Region`, `TrafficType`, `VisitorType` в момент входа требуется подтвердить; числовые коды браузера, системы и источника трафика являются категориями.
- **Ограничение данных:** В файле хранятся итоговые характеристики посещений, а не отдельные снимки сессии в момент входа. Условную модель на заранее известных признаках можно рассматривать только после проверки того, что они реально доступны на входе; если это не подтверждается, запросить подходящие данные.
- **Метрика и валидация:** `roc_auc` - обоснованный начальный выбор для бинарного прогноза при 15,47% покупок, не заданный пользователем. Для предварительной оценки возможно внешнее стратифицированное случайное разбиение, внутренняя валидация AutoGluon - `auto`. Без точных дат и идентификаторов нельзя выдавать такую проверку за тест на будущих сессиях или новых посетителях.

**Кандидат конфигурации** (только после подтверждения доступности оставшихся признаков на входе):

```json
{
  "label": "Revenue",
  "problem_type": "binary",
  "eval_metric": "roc_auc",
  "ignored_columns": [
    "Administrative",
    "Administrative_Duration",
    "Informational",
    "Informational_Duration",
    "ProductRelated",
    "ProductRelated_Duration",
    "BounceRates",
    "ExitRates",
    "PageValues"
  ],
  "validation_procedure": "auto",
  "presets": "medium_quality"
}
```

Положительный класс `Revenue = True` определён по данным; поле `positive_class` здесь не указано, поскольку текущая схема проекта перечисляет строки и числа, но не булевы значения. При явном задании класса нужно согласовать тип метки со схемой или выполнить контролируемое преобразование. `time_limit` подставляет сервис; `ignored_columns` и `validation_procedure` преобразуются обёрткой.

## 4. Критерии проверки агента

- **Обязательные результаты:** агент определяет `Revenue` и `binary`, учитывает момент входа, исключает накопленные и потенциально будущие показатели, проверяет доступность остальных признаков и не обещает достоверную оценку без соответствующих данных.
- **Допустимые альтернативы:** сначала запросить снимки или описание доступных при входе полей; предложить условную конфигурацию на подтверждённых статических признаках. Возможна другая обоснованная бинарная метрика.
- **Критические ошибки:** использовать `PageValues`, просмотры или длительности текущей сессии как уже известные при входе; игнорировать необходимость проверки момента доступности признаков; выдавать случайное разбиение за тест на будущих посетителях.
