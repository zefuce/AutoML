# Olist Brazilian E-Commerce - результат исследования

Задача исследования - изучить девять связанных таблиц Olist, определить пригодность данных для AutoML и построить постановку прогноза задержки доставки на момент оформления заказа. В исходных таблицах нет готовой целевой переменной. Для выбранного сценария она формируется по календарным датам фактической и обещанной доставки.

Данные: [Brazilian E-Commerce Public Dataset by Olist (Kaggle)](https://www.kaggle.com/datasets/olistbr/brazilian-ecommerce). Все приведённые показатели вычислены в `EDA_olist_brazilian_ecommerce.ipynb`.

Для воспроизведения необходим один архив [archive.zip](https://drive.google.com/file/d/1MJsj4x5spwx-jnh2UXj9bi67FW2vlRDN/view?usp=drive_link), содержащий девять файлов: `olist_orders_dataset.csv`, `olist_customers_dataset.csv`, `olist_order_items_dataset.csv`, `olist_order_payments_dataset.csv`, `olist_order_reviews_dataset.csv`, `olist_products_dataset.csv`, `olist_sellers_dataset.csv`, `olist_geolocation_dataset.csv`, `product_category_name_translation.csv`.

Для связей `orders → customers`, `items → orders`, `items → products`, `items → sellers`, `payments → orders`, `reviews → orders` не найдено несопоставленных внешних ключей.

Прямые LEFT JOIN позиций, платежей и отзывов к `orders` дают 119 143 строк вместо 99 441. Сумма исходных платежей составляет 16 008 872,12, а после наивного соединения платежей с позициями и повторного суммирования - 20 470 726,66 (+27,87%). Следовательно, для обучения нужна предварительная агрегация дочерних таблиц до одной строки на заказ. Эта проверка относится к корректности соединения, а не к оценке выручки.

В `customers` содержится 96 096 уникальных `customer_unique_id`. У 2 997 покупателей более одного заказа, максимальное количество - 17. `customer_id` относится к записи заказа и не заменяет устойчивый идентификатор покупателя.

## 3. Формирование целевой переменной

Цель `late_delivery` равна 1, когда календарная дата `order_delivered_customer_date` позже календарной даты `order_estimated_delivery_date`. Она равна 0 при доставке не позже обещанного дня. Для расчёта используются только заказы со статусом `delivered` и обеими заполненными датами.

| Показатель | Значение |
|---|---:|
| Заказов со статусом `delivered` | 96 478 |
| Заказов с определённой меткой | 96 470 |
| `late_delivery = 0` | 89 936 (93,23%) |
| `late_delivery = 1` | 6 534 (6,77%) |
| Исключено из данной постановки | 2 971 |
| Просрочек при сравнении точных timestamp | 7 826 (8,11%) |

Разница между 6 534 и 7 826 возникает из-за времени суток: обещанная дата записана как полночь. Для срока, определённого календарным днём, корректно сравнивать даты, а не точные временные метки. Цель является бинарной с редким положительным классом, но не требует искусственного балансирования до анализа ошибок и метрики.

Ограничение: эта постановка оценивает просрочку среди завершившихся доставкой заказов. На момент оформления неизвестно, будет ли заказ доставлен вообще. Поэтому выводы для всех будущих заказов ограничены возможным смещением отбора; заказы с неизвестным исходом нельзя автоматически кодировать классом 0.

## 5. Товары, платежи и отзывы

Категорий с непустым названием - 73. Для 13 товаров категории не найдены в словаре перевода: 10 записей `portateis_cozinha_e_preparadores_de_alimentos` и 3 записи `pc_gamer`.

Иллюстративная граница временного holdout - `2018-05-26 18:18:03`. Она выбрана по 80-му процентилю упорядоченных размеченных заказов. В базовую обучающую часть дополнительно допускаются только заказы, доставка которых завершилась до этой границы.

Между окончательным train и validation остаются 418 общих `customer_unique_id`, поэтому временная валидация и обобщение на полностью новых покупателей являются различными сценариями.

## 9. Подготовка таблицы для AutoML

В ноутбуке формируется единая витрина на уровне `order_id`: 99 441 строка и 99 441 уникальный заказ. Из них 775 заказов не имеют позиций. Для 96 470 размеченных доставленных заказов позиции присутствуют.

В демонстрационной конфигурации подготовлен 21 признак: штат и почтовый префикс покупателя; месяц, день недели и час покупки; количество позиций, уникальных товаров, продавцов и категорий; общая цена товаров и доставка; средние масса, объём и число фотографий товара; сводная категория товара и штат продавца; количество штатов продавцов; приближённые координаты покупателя и продавцов по почтовому префиксу. Для категорий используются переводы при наличии и исходные значения в остальных случаях.

| Показатель витрины | Значение |
|---|---:|
| Выбранных признаков | 21 |
| Обучающих заказов с доступными к границе метками | 75 128 |
| Валидационных заказов | 19 294 |
| Положительных меток в train | 5 339 |
| Положительных меток в validation | 674 |
| Пропусков `mean_product_photos` среди всех размеченных заказов | 1,38% |
| Пропусков координат покупателя | 0,27% |
| Пропусков координат продавцов | 0,22% |

Прямые идентификаторы `order_id`, `customer_id`, `customer_unique_id`, `product_id`, `seller_id` не передаются как признаки. Метка `late_delivery` в признаки также не входит. Точные даты доставки, итоговый статус, отзыв и подтверждение оплаты исключены, чтобы избежать очевидной утечки при прогнозировании во время покупки. Доступность характеристик каталога и итоговой суммы доставки в момент оформления следует подтвердить перед эксплуатацией.

## 10. Ожидаемые действия AutoML-агента

1. Понять бизнес-запрос о задержке доставки, определить момент прогноза и сформировать цель `late_delivery` сравнением календарных дат.
2. Выделить бинарную классификацию с положительным классом 6,77% и выбрать метрику с учётом стоимости пропуска просрочки и ложного предупреждения; оценку по accuracy не считать достаточной.
3. Различать неизвестные исходы и отрицательный класс. Не размечать отменённые и незавершённые заказы как своевременные.
4. До AutoML агрегировать дочерние таблицы до уровня заказа и проверять сохранение числа уникальных `order_id`, исключая размножение строк и сумм.
5. Отбирать признаки по доступности в момент покупки: запретить фактическую доставку, передачу перевозчику, окончательный статус и отзывы; отдельно проверять доступность платежей и обещанной даты.
6. Применять временную валидацию и обучаться только на уже известных к границе среза метках. При необходимости отдельно оценивать качество на новых `customer_unique_id`.
7. Учитывать пропуски товарных атрибутов, географические неточности, редкий положительный класс и изменения распределений во времени.
8. Передавать подготовленную таблицу AutoGluon только после контроля схемы, целевого столбца, признаков и стратегии валидации.

## Итог

Olist Brazilian E-Commerce подходит для проверки наиболее важных для проекта возможностей: восстановления цели по бизнес-формулировке, построения размеченной выборки из нескольких таблиц, контроля кратности соединений и исключения временных утечек. На данных сформирован воспроизводимый сценарий бинарной классификации задержки доставки с хронологической оценкой. Все девять CSV исследованы; таблицы платежей и отзывов исключены из признаков основного сценария по условиям доступности, но сохранены в EDA для проверки качества и структуры.
