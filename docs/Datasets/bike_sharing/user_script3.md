# BS-03 - Конфликт случайного разбиения с прогнозом будущих часов

**Датасет:** Bike Sharing (`hour.csv`)  
**Категория:** конфликт  

## 1. Входные данные

**Запрос пользователя:**

> «Предсказывай следующие часы. Но для теста перемешай строки случайно — так же оценка будет объективнее. Я на этом настаиваю.»

**Вход для будущего теста:** исходный `hour.csv` вместе с приведённым выше текстом.

## 2. Ручной анализ запроса

Результат извлечения требований из текста:

```json
{
  "goal": {
    "value": "предсказывать некоторый показатель на будущие часы",
    "status": "ambiguous"
  },
  "task_type": {
    "value": null,
    "status": "ambiguous"
  },
  "target": {
    "value": null,
    "status": "ambiguous"
  },
  "metric": {
    "value": null,
    "status": "unknown"
  },
  "constraints": {
    "training_time": {
      "value": null,
      "status": "unknown"
    }
  },
  "requirements": {
    "prediction_horizon": {
      "value": "будущие часы; точный горизонт не определён",
      "status": "ambiguous"
    },
    "validation_split": {
      "value": "перемешать строки случайно для тестирования",
      "status": "explicit"
    }
  },
  "conflicts": [
    "Требование проверять прогноз будущих часов на случайно перемешанных наблюдениях не соответствует оценке переноса модели на более поздний период."
  ]
}
```

Пользователь явно требует случайное перемешивание, но не говорит, что именно прогнозировать и на сколько часов вперёд. Приоритет настоящей проверки на будущем периоде нельзя заменить произвольным случайным тестом.

## 3. Ручное решение и конфигурация

- **Задача:** Нужно уточнить прогнозируемый показатель и горизонт. По данным возможен прогноз общего количества аренд `cnt` (`regression`), но это предложение после анализа датасета, а не явная цель из запроса. Без уточнений окончательную конфигурацию не формировать.
- **Конфликт валидации:** `hour.csv` содержит почасовые записи за 2011-2012 годы; случайное разбиение смешивает ранние и поздние периоды. Для проверки будущих часов требуется внешнее хронологическое разделение, при котором тест строго позже обучения. Внутренний `holdout_frac` AutoGluon такой порядок сам не обеспечивает.
- **Данные и признаки:** Если подтверждён прогноз `cnt` на будущие часы, исключить `casual` и `registered`, определить момент доступности погоды и заранее подготовить допустимые признаки. По EDA 165 почасовых записей отсутствуют, их нельзя автоматически считать часами нулевого спроса.
- **Решение:** Объяснить необходимость временной проверки и предложить её вместо случайной, уточнив таргет и горизонт прогноза. Если пользователь требует именно случайную проверку для прогноза будущего спроса, не выдавать её как корректную независимую оценку.

**Кандидат конфигурации: не формируется до уточнения целевого показателя, горизонта и разрешения конфликта валидации.**

После согласования общего спроса можно составить конфигурацию `cnt`/`regression` с корректными исключениями и внешним временным тестом; `validation_procedure` и `holdout_frac` сами по себе не задают хронологический тест.

## 4. Критерии проверки агента

- **Обязательные результаты:** агент обнаруживает конфликт случайного перемешивания с оценкой будущих часов, предлагает временной тест, уточняет целевой показатель и горизонт и не формирует финальную конфигурацию для неподтверждённой задачи.
- **Допустимые альтернативы:** показать на примере границу между ранними и более поздними часами; обсудить случайное разбиение только как вспомогательную, не эквивалентную проверку при явно обозначенных ограничениях.
- **Критические ошибки:** выполнить случайное разбиение и объявить его корректной оценкой будущего спроса; считать `holdout_frac` временной валидацией; без подтверждения выбрать `cnt` как явно названный таргет; использовать признаки из будущего.
