# BS-02 - Прогноз спроса с погодой и распределением по станциям

**Датасет:** Bike Sharing (`hour.csv`)  
**Категория:** длинный  

## 1. Входные данные

**Запрос пользователя:**

> «Для сервиса проката важно предсказывать число аренд на следующий час, чтобы заранее распределять велосипеды между станциями. Мы можем получать прогноз погоды, поэтому хотелось бы учесть температуру, влажность и ветер. Но тот файл, который я загрузил, содержит только фактические погодные показатели за каждый час; отдельной истории того, что прогнозировалось заранее, у меня нет. Можно ли честно протестировать модель с погодой на этих данных? Если нет, предложи вариант без будущих измерений и объясни, какие дополнительные данные потребуются.»

**Вход для будущего теста:** исходный `hour.csv` вместе с приведённым выше текстом.

## 3. Ручное решение и конфигурация

- **Задача:** По EDA `cnt` - общий спрос за час (`regression`), а признаков отдельных станций в `hour.csv` нет. Общий прогноз не позволяет автоматически определить, сколько велосипедов потребуется на каждой станции; для такой задачи нужны исторические данные по станциям и отдельная постановка.
- **Погода:** В данных `temp`, `atemp`, `hum`, `windspeed`, `weathersit` - фактические показания соответствующего часа. Прогноз погоды, получаемый заранее, не равен этому измерению; без архива прогнозов нельзя честно проверить модель, обучаемую и оцениваемую будто прогнозы уже были доступны.
- **Вариант без будущих измерений:** Для суммарного числа аренд предложить табличную регрессию по календарю прогнозируемого часа. Исключить `casual`, `registered`, `instant` и фактическую погоду будущего часа. Чтобы учитывать погоду в будущем, потребуются исторические прогнозы с отметками времени их получения и сопоставлением с прогнозируемым часом.
- **Метрика и проверка:** Для общего спроса допустима `mean_absolute_error` либо `root_mean_squared_error`. Обязательно внешнее временное разделение по `dteday` и `hr`, без перемешивания. Пропущенные 165 часов не заменять нулевым спросом; это не отдельные нулевые наблюдения.

**Кандидат конфигурации для общего почасового спроса без погодных признаков** (после проверки указанных условий):

```json
{
  "label": "cnt",

  "ignored_columns": [

```

До запуска следует сообщить о невозможности оценить распределение по станциям на данном файле и согласовать использование только общего спроса. Для модели с погодными прогнозами нужны дополнительные исторические данные. `validation_procedure = "auto"` не реализует внешнее хронологическое разбиение; `time_limit` подставляет сервис.

## 4. Критерии проверки агента

- **Обязательные результаты:** агент различает фактическую погоду и её прогноз, не подменяет одну другой, исключает будущее наблюдение и компоненты `cnt`, сообщает об отсутствии данных по станциям, предлагает выполнимую модель общего спроса без погоды и перечисляет дополнительные данные.
- **Допустимые альтернативы:** предложить календарную модель с лагами, если их подготовка поддерживается и не вносит утечек; уточнить, достаточно ли пользователю общего спроса, либо попросить данные по станциям и архивы погодных прогнозов.
- **Критические ошибки:** утверждать, что `hour.csv` содержит распределение аренд по станциям; использовать фактическую погоду следующего часа как заранее известный прогноз; включить `casual`/`registered`; считать случайное разбиение корректной проверкой будущих часов; обещать честное тестирование погодных прогнозов без архива прогнозов.
