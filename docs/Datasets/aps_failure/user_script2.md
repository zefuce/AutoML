# APS-02 - Минимизация стоимости ошибок диагностики

**Датасет:** APS Failure (`aps_failure_training_set.csv`)  
**Категория:** стоимость ошибок  

## 1. Входные данные

**Запрос пользователя:**

> «У нас два типа ошибки. Лишняя проверка исправного грузовика обходится примерно в 10 условных единиц, пропущенная неисправность APS — в 500. Мы хотим минимизировать суммарные потери, а не просто получить красивый процент точности. Предложи адекватную конфигурацию, но не подменяй денежный критерий стандартной метрикой.»

**Вход для будущего теста:** исходный `aps_failure_training_set.csv` вместе с приведённым выше текстом.

Пользователь явно задаёт бизнес-функцию потерь, но не задаёт встроенную метрику AutoGluon. Несовместимости требований между собой нет; ограничение появляется при сопоставлении с доступными параметрами проекта.

## 3. Ручное решение и конфигурация

- **Задача:** `label = "class"`, `problem_type = "binary"`, положительный класс `pos`. Доля `pos` в обучающей выборке - 1,67%; доля правильных ответов не отражает заявленную стоимость пропусков.
- **Стоимость ошибок:** Итоговый критерий - `10 * FP + 500 * FN`, рассчитанный по прогнозам на независимых данных. `FP` - ошибочное направление исправного грузовика на проверку, `FN` - пропущенный отказ APS. Одна стандартная `accuracy`, `recall` или `roc_auc` не равна этой функции потерь.
- **Метрика и порог:** `roc_auc` может использоваться как промежуточная метрика выбора модели и ранжирования рисков, но не как замена денежной цели. Если доступны вероятности и реализована дополнительная логика, порог выбирают по стоимости на валидационной части, не на финальном тесте. Без поддержки такого расчёта система должна явно сообщить об ограничении.
- **Данные и валидация:** Распознать `na` как пропуски, сохранить редкий класс `pos` при разбиении. Официальный тестовый файл не использовать для выбора модели или порога; его подключение требует отдельной поддержки сервиса.

**Кандидат конфигурации** (для предварительного выбора модели; денежная цель оценивается отдельно):

```json
{
  "label": "class",
  "problem_type": "binary",
  "positive_class": "pos",
  "eval_metric": "roc_auc",
  "validation_procedure": "auto",
  "presets": "medium_quality"
}
```

Кандидат не является полным решением пользовательской задачи: для оптимизации затрат необходим отдельный расчёт `FP`, `FN`, стоимости и, при наличии поддержки, подбор порога на валидации. Подмена бизнес-критерия значением `eval_metric = "roc_auc"` недопустима. `time_limit` задаётся сервисом по умолчанию.

## 4. Критерии проверки агента

- **Обязательные результаты:** агент определяет класс `pos`, сохраняет затраты FP = 10 и FN = 500, формулирует `10 * FP + 500 * FN` и отделяет эту цель от встроенного `eval_metric`. Не использует финальный тест для подбора порога.
- **Допустимые альтернативы:** `roc_auc`, `recall` или другая обоснованная вспомогательная метрика; отдельная стоимостная оценка при наличии нужного расширения либо честное сообщение о его отсутствии.
- **Критические ошибки:** считать `recall` или `roc_auc` прямой минимизацией стоимости; перепутать цены FP и FN; оптимизировать лишь `accuracy`; подобрать порог на финальном тесте или обещать денежный оптимум без расчёта стоимости.
