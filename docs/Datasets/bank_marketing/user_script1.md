# BM-01 — Прогноз согласия на депозит до первого звонка

**Датасет:** Bank Marketing (`bank-full.csv`)  
**Категория:** длинный, бессвязный запрос с посторонней информацией  

## 1. Входные данные

**Запрос пользователя (без изменений из общей матрицы):**

> «Слушай, я тут с этими таблицами совсем запутался. У нас банк, ну точнее отдел, который клиентам звонит, и начальник постоянно спрашивает, почему мы столько времени тратим. Ещё у нас отчёты по понедельникам, но это сейчас вообще неважно. В общем, есть файл с клиентами и какими-то цифрами, там вроде кому-то уже звонили, а кому-то нет, я не все названия колонок понимаю. И вообще мы сначала думали просто всех обзвонить, но потом решили, что это не очень. Нужно как-то заранее понять, кто согласится на депозит, а кто нет. Только заранее — это до первого звонка в текущей кампании, потому что после разговора уже поздно решать, кому звонить. Там ещё есть длительность звонков, кажется, и что-то про предыдущие кампании. Согласившихся вроде намного меньше, хотя я точно не считал. Короче, можно по этой таблице понять, с кого лучше начинать обзвон? И чтобы модель не использовала информацию, которую мы узнаем только после разговора. А то начальству потом объяснять.»

**Вход для будущего теста:** исходный `bank-full.csv` вместе с приведённым выше текстом.

## 3. Ручное решение и конфигурация

- **Задача:** `label = "y"`, `problem_type = "binary"`, положительный класс `yes`. По EDA доля `yes` — **11,70%**; классы несбалансированы.
- **Признаки:** исключить `duration` (результат звонка). Для прогноза до первого звонка также исключить исходные `campaign`, `contact`, `day`, `month`, связанные с текущим/последним контактом. Уточнить доступность оставшихся сведений на момент прогноза, особенно истории прошлых кампаний.
- **Метрика:** `roc_auc` — допустимый начальный выбор для ранжирования клиентов, **не указанный пользователем**. Другая обоснованная метрика допустима; порог для звонка нельзя выбирать без дополнительных бизнес-условий.
- **Валидация:** воспроизводимое стратифицированное случайное разбиение возможно лишь как предварительная оценка. Не выдавать его за проверку на будущей кампании: в датасете нет полной хронологии.

**Кандидат конфигурации** (после проверки доступности оставшихся признаков):

```json
{
  "label": "y",
  "problem_type": "binary",
  "positive_class": "yes",
  "eval_metric": "roc_auc",
  "ignored_columns": ["duration", "campaign", "contact", "day", "month"],
  "validation_procedure": "auto",
  "presets": "medium_quality"
}
```

`time_limit` не указан пользователем: перед запуском сервис должен подставить свой лимит. `ignored_columns` и `validation_procedure` обрабатываются обёрткой, а не передаются в `fit()` как одноимённые аргументы.
