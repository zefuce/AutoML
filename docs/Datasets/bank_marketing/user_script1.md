# BM-01 - Прогноз согласия на депозит до первого звонка

**Датасет:** Bank Marketing (`bank-full.csv`)  
**Категория:** длинный, бессвязный запрос с посторонней информацией  

## 1. Входные данные

**Запрос пользователя:**

> «Слушай, я тут с этими таблицами совсем запутался. У нас банк, ну точнее отдел, который клиентам звонит, и начальник постоянно спрашивает, почему мы столько времени тратим. Еще у нас отчеты по понедельникам, но это сейчас вообще неважно. В общем, есть файл с клиентами и какими-то цифрами, там вроде кому-то уже звонили, а кому-то нет, я не все названия колонок понимаю. И вообще мы сначала думали просто всех обзвонить, но потом решили, что это не очень. Нужно как-то заранее понять, кто согласится на депозит, а кто нет. Только заранее - это до первого звонка в текущей кампании, потому что после разговора уже поздно решать, кому звонить. Там еще есть длительность звонков, кажется, и что-то про предыдущие кампании. Согласившихся вроде намного меньше, хотя я точно не считал. Короче, можно по этой таблице понять, с кого лучше начинать обзвон? И чтобы модель не использовала информацию, которую мы узнаем только после разговора. А то начальству потом объяснять.»

**Вход для будущего теста:** исходный `bank-full.csv` вместе с приведённым выше текстом.

## 3. Ручное решение и конфигурация

- **Задача:** `label = "y"`, `problem_type = "binary"`, положительный класс `yes`. Таргет отражает факт подписки клиента на депозит. По EDA доля `yes` - 11,70%; классы несбалансированы.
- **Признаки:** исключить `duration` (продолжительность последнего звонка, неизвестная до его проведения). Для прогноза до первого звонка также исключить исходные `campaign`, `contact`, `day`, `month`, связанные с текущим/последним контактом. Проверить доступность остальных признаков до первого звонка, включая сведения о предыдущих контактах с клиентом (`previous`, `pdays`, `poutcome`).
- **Метрика:** `roc_auc` - допустимый начальный выбор для ранжирования клиентов, не указанный пользователем. Другая обоснованная метрика допустима; порог для звонка нельзя выбирать без дополнительных бизнес-условий.
- **Валидация:** независимую тестовую выборку можно выделить стратифицированным случайным разбиением до обучения; внутренняя валидация AutoGluon - `auto`. Такая оценка предварительная и не заменяет проверку на будущей кампании: в датасете нет полной хронологии.

**Кандидат конфигурации** (после проверки доступности оставшихся признаков):

```json
{
  "label": "y",
  "problem_type": "binary",
  "positive_class": "yes",
  "eval_metric": "roc_auc",
  "ignored_columns": ["duration", "campaign", "contact", "day", "month"],
  "validation_procedure": "auto",
  "presets": "medium_quality"
}
```

`time_limit` не указан пользователем: перед запуском сервис должен подставить свой лимит. `ignored_columns` и `validation_procedure` обрабатываются обёрткой, а не передаются в `fit()` как одноимённые аргументы.

## 4. Критерии проверки агента

- **Обязательные результаты:** агент выделяет задачу и момент прогноза из длинного текста; определяет `y`, `binary` и класс `yes`; исключает `duration` и признаки, недоступные до первого звонка, проверяет доступность остальных. Учитывает дисбаланс, обосновывает метрику и не выдаёт случайное разбиение за проверку на будущей кампании.
- **Допустимые альтернативы:** другая обоснованная метрика вместо `roc_auc`; уточняющий вопрос о доступности признаков до формирования окончательной конфигурации. Конкретные формулировки и порядок действий агента не обязаны совпадать с эталоном.
- **Критические ошибки:** использование `duration` или иных сведений из будущего; неверный таргет или тип задачи; приписывание пользователю неуказанной метрики или лимита обучения; запуск с неподтверждённо доступными признаками.
